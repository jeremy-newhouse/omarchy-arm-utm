Build log · August 2026

Omarchy on Apple Silicon

How to rebuild the Omarchy desktop on Arch Linux ARM inside UTM, why the official path is closed, and the ten obstacles that only surface once you hit them.

HostMacBook M3 Max · macOS 26 GuestArch Linux ARM aarch64 AccelerationHVF, no emulation Result3.6 GB, distributable

Context

The starting point

Omarchy is DHH's desktop distribution: Arch Linux with Hyprland, polished themes, and about 430 bespoke utilities. The question was simple: can you have that in a virtual machine on an Apple Silicon Mac?

There's a reference guide, the repository's discussion #452, that describes exactly that. The problem is it's from 2025, and the project moves fast.

First: check whether the guide still holds

Four checks were enough to rule it out. None require installing anything:

# 1. The endpoint the guide uses
curl -sI https://omarchy.org/install-bare | head -1
→ HTTP/2 404

# 2. The Omarchy mirror, for aarch64
curl -sI https://stable-mirror.omarchy.org/core/os/aarch64/core.db | head -1
→ HTTP/2 404   (the x86_64 one returns 200)

# 3. The installer's guard
curl -s .../master/install/preflight/guard.sh | grep -A2 'x86 only'
→ if [[ $(uname -m) != "x86_64" ]]; then
→   abort "x86_64 CPU"

# 4. The real state of ARM support, in the ISO repo
curl -s .../omarchy-iso/main/plans/aarch64-support.md | head -20
→ "Plan: aarch64 ... Target: a parallel generic UEFI aarch64 ISO"

That fourth point is the most informative: the Omarchy team has already written the plan for supporting aarch64, and in that document they list their own blockers. Among others: “pkgs.omarchy.org/{stable,edge}/aarch64/ must serve a real repo. Probed today, both return 404”.

One detail seals it. The Omarchy installer does this:

echo 'Server = https://stable-mirror.omarchy.org/$repo/os/$arch' \
  | sudo tee /etc/pacman.d/mirrorlist

It overwrites the entire mirror list. On ARM, the next pacman -Syu fails, because that mirror doesn't serve aarch64. In quattro this lives in install/post-install/pacman.sh.

Correction: in quattro that guard no longer exists

Months later I checked again and point 3 was no longer true. Cloning both branches:

Branchinstall/preflight/guard.shuname -m across the repo
master (3.8.x)exists, line 251 occurrence
quattro (4.x, the default)the preflight/ directory doesn't exist0 occurrences

Omarchy 4 doesn't refuse to run on ARM64. What's missing is the repository: the tree is shell, Lua, and QML, architecture-agnostic, and the omarchy package declares arch=('any'). The blocker went from “it refuses” to “there's nowhere to install from,” which is a much smaller problem —publishing about 25 aarch64 packages would close it— and explains why several third-party projects have had to stand up their own separate repository.

I'm leaving the mistake in view instead of rewriting the history, because it's representative: I checked against the wrong branch. master sounds like the main branch; in this repository the default is quattro. The same trap that had already cost me an emergency-mode boot, again, in a different place.

Decision

Rebuild instead of install

If Omarchy can't be installed, it can be rebuilt: stand up Arch Linux ARM with Hyprland and apply the actual content of the Omarchy repository —configuration, themes, utilities—, which is where 90 % of the experience lives.

Before writing a line of code, it's worth measuring whether that yields something usable. You can tell without installing anything, by cross-referencing Omarchy's package list against the Arch Linux ARM index: 

# Arch Linux ARM package index for aarch64
curl -s http://mirror.archlinuxarm.org/aarch64/core/core.db   -o core.db
curl -s http://mirror.archlinuxarm.org/aarch64/extra/extra.db -o extra.db
mkdir db && cd db && tar -xzf ../core.db && tar -xzf ../extra.db
ls -1 | sed -E 's/-[^-]+-[^-]+$//' | sort -u > ../alarm.txt

# Omarchy package list
curl -s .../omarchy/quattro/install/omarchy-base.packages \
  | grep -vE '^#|^$' > omarchy.txt

comm -12 <(sort omarchy.txt) ../alarm.txt | wc -l   # available
comm -23 <(sort omarchy.txt) ../alarm.txt           # the ones missing

Result: 121 of 148 packages exist on ARM under their exact name (123 once you substitute nvim→neovim and ttf-jetbrains-mono-nerd-basic→ttf-jetbrains-mono-nerd, which is what the prepare phase does). The missing ones are proprietary apps (1Password, Spotify, Obsidian, Typora) and Omarchy's own packages. And the important part: hyprland, hyprlock, hypridle, quickshell, uwsm, sddm, mesa, and chromium are all there, at current versions. Arch Linux ARM keeps pace with Arch: firefox 154.0-1 on both.

With those numbers, the project makes sense.

Architecture

How it's built

Three structural decisions, each with its own reason.

Headless build. Booting an installer and clicking through isn't reproducible. The whole process runs in a QEMU VM driven by expect over the serial console. If something fails, you fix the script and rerun it.

HVF acceleration. Since the guest is aarch64 and so is the host, you can use macOS's native hypervisor instead of emulating. The difference is an order of magnitude.

Alpine as the boot environment. Arch Linux ARM doesn't publish an installer ISO, only a rootfs tarball. You need a minimal Linux that can partition the disk and deploy that tarball. Alpine virt weighs 88 MB, boots in seconds, and drops straight into a serial console. 

Alpine live (QEMU + HVF, serial console)
  └─ stage 1: partition, deploy ALARM rootfs, chroot
       └─ stage 2 (root): kernel, UEFI boot, packages, user
            └─ stage 3 (user): Omarchy, AUR, themes

Step by step

The procedure

1 · Dependencies

brew install qemu expect aria2
brew install --cask utm

2 · Base images, with verification

aria2c -x8 https://dl-cdn.alpinelinux.org/alpine/v3.24/releases/aarch64/alpine-virt-3.24.1-aarch64.iso
aria2c -x8 http://os.archlinuxarm.org/os/ArchLinuxARM-aarch64-latest.tar.gz

# The tarball gets rebuilt every few weeks: always verify
curl -s http://os.archlinuxarm.org/os/ArchLinuxARM-aarch64-latest.tar.gz.md5
md5 -q ArchLinuxARM-aarch64-latest.tar.gz

3 · Partitioning and rootfs deployment

Inside Alpine. First non-obvious detail: you have to load the btrfs module by hand. Alpine's virt kernel ships it as a module but doesn't autoload it, and mkfs.btrfs works —it's userspace— while mount fails with a baffling “Invalid argument.” 

modprobe btrfs vfat
grep -qw btrfs /proc/filesystems || exit 1   # actually verify

parted -s /dev/vda mklabel gpt
parted -s /dev/vda mkpart OMBOOT fat32 1MiB 1025MiB
parted -s /dev/vda set 1 esp on
parted -s /dev/vda mkpart OMROOT btrfs 1025MiB 100%
mkfs.vfat -F32 -n OMBOOT /dev/vda1
mkfs.btrfs -f -L OMROOT  /dev/vda2

mount /dev/vda2 /mnt
btrfs subvolume create /mnt/@
btrfs subvolume create /mnt/@home
umount /mnt
mount -o rw,noatime,compress=zstd:3,subvol=@     /dev/vda2 /mnt
mkdir -p /mnt/home
mount -o rw,noatime,compress=zstd:3,subvol=@home /dev/vda2 /mnt/home

Mount order

The ESP is mounted after extracting the rootfs. The ALARM tarball contains symlinks under /boot, and vfat doesn't support them: if the ESP is mounted during extraction, bsdtar fails. Extract first, discard that /boot, and let pacman repopulate it once the ESP is mounted. 

bsdtar -xpf alarm-rootfs.tgz -C /mnt      # -p preserves permissions and xattrs
rm -rf /mnt/boot && mkdir /mnt/boot
mount /dev/vda1 /mnt/boot

4 · Base system and UEFI boot

Inside the chroot. Arch Linux ARM has its own keyring, distinct from Arch's: 

pacman-key --init
pacman-key --populate archlinuxarm     # not "archlinux"
pacman -Syu --noconfirm
pacman -S --noconfirm --needed base base-devel linux-aarch64 sudo git \
  networkmanager btrfs-progs dosfstools efibootmgr

The initramfs needs the virtio modules listed explicitly, because mkinitcpio's autodetect runs in a chroot where the running kernel is Alpine's: 

sed -i 's/^MODULES=.*/MODULES=(virtio virtio_pci virtio_blk virtio_scsi virtio_net virtio_gpu btrfs)/' \
  /etc/mkinitcpio.conf
mkinitcpio -P

And here's the detail that decides whether the VM boots at all:

bootctl --esp-path=/boot --no-variables install

--no-variables avoids writing entries to UEFI NVRAM. Why? Because the build VM's NVRAM doesn't travel to the UTM bundle: they're separate variable files. Boot has to rely on the fallback path \EFI\BOOT\BOOTAA64.EFI, which bootctl installs regardless. If you rely on NVRAM, the VM builds fine and then won't boot.

5 · Omarchy

Two lines and you're done — in theory:

git clone --depth 1 https://github.com/basecamp/omarchy.git ~/.local/share/omarchy
cp -R ~/.local/share/omarchy/config/* ~/.config/

In practice, Hyprland booted into emergency mode:

⚠ Emergency mode tripped: A lua config error resulted in no binds being registered.
cannot open /usr/share/omarchy/default/hypr/bootstrap.lua: No such file or directory

What comes next is the part no guide covers.

Findings

The six obstacles

Finding 01 · Repository

git clone doesn't get you master

curl -s https://api.github.com/repos/basecamp/omarchy | jq -r .default_branch
→ quattro

curl -s .../omarchy/master/version    → 3.8.5
curl -s .../omarchy/quattro/version   → 4.0.0.alpha

The default branch is not master. A git clone without --branch gets you quattro, which is Omarchy 4 — a different product from the 3.8.5 that master documents:

master (3.8.5)quattro (4.x)
Barwaybarquickshell
Hyprland config.conf filesLua
Distributionscripts in $HOMEpacman package

Practical consequence: I had installed master's package list —with waybar— on a system running quattro, which uses quickshell. The bar simply didn't exist. And quickshell 0.3.1 is available on Arch Linux ARM; I just didn't know it was needed.

Lesson: when a project moves fast, check the default branch before reading its documentation.

Finding 02 · Distribution

Omarchy 4 is a pacman package

Version 4 ships as a package, not as scripts in $HOME. That package places files at fixed system paths:

  • /usr/share/omarchy — the full tree
  • /usr/bin/omarchy-* — the binaries on PATH
  • /etc/profile.d/omarchy.sh — the shell hook
  • /usr/share/uwsm/env.d/10-omarchy — the graphical-session hook

Worth being precise here, because I got this wrong myself at first: the package is not x86_64-only. Its PKGBUILD declares arch=('any') —it's shell scripts, Lua, and QML— and installs the commands to /usr/bin, with links from /usr/share/omarchy/bin. What's x86_64-only is the repository it's published from. On ARM there's nowhere to install it from, and that's where the problem starts: cloning the repository into $HOME leaves OMARCHY_PATH undefined, .bashrc throws an error, Hyprland can't find its bootstrap.lua, and nothing in autostart works. 

sudo ln -sfn "$OMARCHY_PATH" /usr/share/omarchy
for f in "$OMARCHY_PATH"/bin/*; do
  sudo ln -sfn "$f" "/usr/bin/$(basename "$f")"           # 439 binaries
done
sudo install -Dm644 "$OMARCHY_PATH/etc/profile.d/omarchy.sh" /etc/profile.d/omarchy.sh
sudo install -Dm644 "$OMARCHY_PATH/default/uwsm/env.d/10-omarchy" \
  /usr/share/uwsm/env.d/10-omarchy

This ended up in /usr/bin, not /usr/local/bin. I started with /usr/local/bin to stay off pacman's turf, which seemed like the clean choice, and it broke things: the Omarchy tree has /usr/bin/omarchy-* hardcoded in thirteen places, five of them .service files. /usr/local/bin is still used, but only for the ARM-specific wrappers that need to win on PATH.

Aside

Omarchy has a mechanism built for exactly this, omarchy-dev-link, which writes /etc/omarchy.conf to point the system at a local checkout. It exists for developing Omarchy itself, but it works just as well here.

Finding 03 · Keyboard

The Super key, hijacked by macOS

Omarchy uses SUPER for everything. On a Mac, SUPER is Cmd, and macOS intercepts Cmd before UTM ever sees it: Cmd+Space opens Spotlight, not the Omarchy menu.

You can fight UTM's input-capture permissions, or fix it inside the guest in one line: 

-- ~/.config/hypr/input.lua
hl.config({
  input = {
    kb_layout  = "es",
    kb_options = "compose:caps,shift:both_capslock_cancel,altwin:swap_lalt_lwin",
  },
})

altwin:swap_lalt_lwin swaps Alt and Super. Result: the Option (⌥) key acts as SUPER, and macOS doesn't intercept Option+Space.

Along the way, another detail: Hyprland reads the keyboard layout from XKBLAYOUT in /etc/vconsole.conf, not KEYMAP. Setting only KEYMAP=es leaves Hyprland on us. You have to write both.

Finding 04 · Rendering

Windows that open invisible

The most baffling symptom: the desktop rendered, the keyboard worked, menus appeared… but opening a terminal produced nothing. hyprctl confirmed it: 

Window aaaad1ec7630 -> Alacritty:
    mapped: 1
    size: 1896,1150
    workspace: 1

Window mapped, with a size, on the visible workspace. And on screen, just the wallpaper. The test that isolated it was comparing two terminals: 

foot       # draws with shared-memory buffers (wl_shm)  → VISIBLE
alacritty  # draws with EGL/GPU (dma-buf)                 → NOT VISIBLE

In other words: under virtio-gpu with virgl, GPU-backed clients produce buffers that Hyprland can't composite. The compositor renders its own elements —bar, wallpaper, menus— but application windows stay empty.

What doesn't fix it, checked one by one:

  • AQ_NO_MODIFIERS=1 — already active
  • render:explicit_sync — removed in Hyprland 0.56
  • render:cm_enabled = false — no effect

What does:

# /etc/environment.d/90-vm-graphics.conf
LIBGL_ALWAYS_SOFTWARE=1

Mesa falls back to llvmpipe, clients deliver wl_shm buffers, and everything renders. The cost is real: you lose GL acceleration inside the VM. As a tradeoff, it's worth turning off blur and shadows, which get expensive with CPU rendering.

The methodology error

Testing it over SSH, it looked like it didn't work. /etc/environment.d/ is read by systemd's session manager, not a login shell: an app launched from SSH doesn't inherit the variable; one launched from the graphical session does. The bug was in the test method, not the fix.

Finding 05 · Resolution

Changing the mode live breaks rendering

Setting 1920×1200 with hyprctl reload left the screen blank. The layers were still there —hyprctl layers listed them, with alpha 1— but nothing painted. Restarting the shell wasn't enough; the whole VM had to be rebooted. Applied from boot, the same resolution works fine. 

-- ~/.config/hypr/monitors.lua
hl.env("GDK_SCALE", "1")
hl.monitor({ output = "Virtual-1", mode = "1920x1200@60", position = "0x0", scale = 1 })

If you touch that file, reboot the VM instead of reloading the config. The scale = 1 matters too: Omarchy assumes retina displays, and with the default value everything comes out oversized in a VM.

Finding 06 · Updates

omarchy-update kept blowing up

Updating ended in an error. The pacman log told the story:

Running 'pacman -Rns --noconfirm dust'      → removed
Running 'pacman -S --noconfirm tensaku'     → doesn't exist on ARM → error

An Omarchy migration had removed dust to replace it with tensaku, an in-house package that doesn't exist on ARM. It left the system with neither. The root cause was in the build: 

ls ~/.local/state/omarchy/migrations | wc -l   → 8
ls /usr/share/omarchy/migrations/*.sh | wc -l  → 83

A normal Omarchy installer stamps all migrations as done when it finishes, because a freshly installed system is already born in the final state: migrations exist to update older installs. Cloning the repository without stamping them meant omarchy-update tried to replay 75 historical migrations.

Two fixes. The first, stamp them:

mkdir -p ~/.local/state/omarchy/migrations
for f in /usr/share/omarchy/migrations/*.sh; do
  : > ~/.local/state/omarchy/migrations/"$(basename "$f")"
done

The second is the one that matters long-term. omarchy-pkg-add aborts if a package doesn't exist, and that takes down the whole update. A wrapper in /usr/local/bin makes it tolerant: 

REAL=/usr/share/omarchy/bin/omarchy-pkg-add
avail=(); skip=()
for p in "$@"; do
  if pacman -Q "$p" &>/dev/null || pacman -Si "$p" &>/dev/null; then
    avail+=("$p")
  else
    skip+=("$p")
  fi
done
((${#skip[@]})) && printf 'Skipped, not available on ARM: %s\n' "${skip[*]}" >&2
((${#avail[@]})) || exit 0
exec "$REAL" "${avail[@]}"

Without this, every new package Omarchy introduces would break updates all over again.

Finding 07 · Verification

The gray desktop: two bugs no log ever flagged

The last check before packaging was looking at a screenshot of the already-sanitized desktop. It booted, the bar was there, the clock showed the time. But the wallpaper was flat gray and notifications were unstyled gray boxes. Not one error in journalctl, not one warning on screen. Two independent causes, and both with the same shape: the system kept working, just wrong.

grep -r doesn't see through a symlink's target. Renaming the user from gabriel to omarchy, I was verifying the result like this: 

grep -rl '\bgabriel\b' /etc /home/omarchy/.config   → 0 matches

Zero. Clean. Except a symlink's target isn't contents of a file: grep doesn't read it. And Omarchy stores the active theme and wallpaper precisely as links. The right check uses a different tool: 

find /home/$NEW /etc /usr/local /opt -xdev -type l -lname "*/home/$OLD/*"
→ 439 dangling links

Four hundred thirty-nine, including the 431 omarchy-* commands in /usr/local/bin, which pointed at a home that no longer existed. The desktop booted because quickshell reads from /usr/share/omarchy, but any command from the menu would have failed.

I had installed four packages that Omarchy 4 retires. The second bug was entirely mine: my “infrastructure” package list came from reading Omarchy 3 and carried over mako, swayosd, walker, and elephant. None of them are in quattro's omarchy-base.packages, and the repository's documentation says so plainly, in docs/notifications.md:

The shell is the notification daemon […] There is no dunst or mako.

mako isn't inert: it activates over D-Bus on the first notify-send and claims org.freedesktop.Notifications before the shell does. quickshell loses the bus name and notifications render with mako's default styling. That's what the gray boxes were. The launcher didn't need walker either: in quattro the menu is a quickshell panel (omarchy-shell shell toggle omarchy.menu), so my fuzzel-based substitute was dead code from day one.

The lesson isn't “a package slipped through.” It's that a distribution's package list is a statement about its architecture, not an inventory. I filled it in from what I remembered of the previous version and reintroduced a component the new one had deliberately replaced.

Methodology error

“Not available” is not a category

Cross-referencing Omarchy's package list against the Arch Linux ARM index turned up 25 gaps. I dumped all of them into the same bucket —“not available”— and moved on. That was a mistake, and it took too long to catch.

That bucket conflated two incomparable things:

  • Impossible: 1Password, Spotify, Obsidian, Typora, pinta (.NET). Proprietary binaries built only for x86_64.
  • Nobody has built it yet: almost everything else.

Working reactively —building only what broke something visible— I ended up chasing down walker and elephant thinking there was no launcher without them (false: the menu is a quickshell panel, see finding 07), xdg-terminal-exec because it's $TERMINAL, and ttfx only once the screensaver threw an on-screen error. The rest stayed in the bucket.

The audit I should have run on day one comes down to two calls to the GitHub API and one to AUR's: 

# Does it exist in AUR?
curl -s "https://aur.archlinux.org/rpc/v5/info?arg[]=tensaku&arg[]=aether" \
  | jq -r '.results[] | "\(.Name) \(.Version) \(.URL)"'

# What language is it written in? (decides if it's portable)
curl -s https://api.github.com/repos/omacom-io/omacalc | jq -r '.language'

# What does its PKGBUILD say?
curl -s .../omarchy-pkgs/master/pkgbuilds/omacalc/PKGBUILD | grep -E '^arch='

The result blows the bucket apart:

PackageSourceLanguageWhy it was missing
omacalc omacut omawriteomacom-ioQt / C++its PKGBUILD already declares aarch64
aether cliampAURGoportable
herdr tensakuAUR / omacomRustarch=(x86_64) by default

Of the 25 gaps, 16 were buildable, and three of those didn't even need any changes: just someone running makepkg on an ARM machine.

Building them

The key observation is that many PKGBUILDs declare arch=(x86_64) because the maintainer only builds for their own machine, not because the code is incompatible. If it's portable Rust, Go, or C++, adding the architecture is enough: 

build_omarchy_tool() {                 # <aur|omapkgs> <package>
  local src="$1" pkg="$2"
  local dir="/tmp/omabuild/$pkg"
  pacman -Q "$pkg" >/dev/null 2>&1 && return 0

  case "$src" in
    aur) git clone --depth 1 -q "https://aur.archlinux.org/$pkg.git" "$dir" ;;
    omapkgs)
      git clone --depth 1 --filter=blob:none --sparse -q \
        https://github.com/omacom-io/omarchy-pkgs.git "$dir/repo"
      ( cd "$dir/repo" && git sparse-checkout set "pkgbuilds/$pkg" )
      cp -a "$dir/repo/pkgbuilds/$pkg/." "$dir/" && rm -rf "$dir/repo" ;;
  esac

  # The whole point: declare aarch64 when the code is portable
  grep -qE "^arch=.*(aarch64|'any')" "$dir/PKGBUILD" || \
    sed -i "s/^arch=(\(.*\))/arch=(\1 'aarch64')/" "$dir/PKGBUILD"

  ( cd "$dir" && makepkg -si --noconfirm --needed )
}

They build in order of increasing cost —data, Go, Qt, Rust— and none is fatal: if one fails, the rest continue. 

for spec in \
  aur:yaru-icon-theme aur:ttf-ia-writer aur:tzupdate aur:ufw-docker \
  omapkgs:omarchy-nvim omapkgs:tobi-try aur:mise-bin \
  aur:aether aur:cliamp \
  omapkgs:omacalc omapkgs:omacut omapkgs:omawrite \
  aur:herdr omapkgs:tensaku omapkgs:hyprland-preview-share-picker; do
  build_omarchy_tool "${spec%%:*}" "${spec#*:}"
done

And ttfx, which isn't in AUR, straight from its repository:

git clone https://github.com/omacom-io/ttfx.git && cd ttfx
cargo build --release && sudo install -Dm755 target/release/ttfx /usr/local/bin/ttfx

The result

Of the 25 gaps, 20 ended up installed. Only one held out, and for a specific reason: herdr invokes zig fetch with Zig 0.15 semantics while the repos are already on 0.16 —the same zig 0.16.0-1 on ARM as on x86_64, so this isn't an ARM thing— and it fails with “no build.zig file found”. Building Zig 0.15 from source is hours of work, and it's a dev tool, not part of the desktop. The remaining gaps are the genuinely impossible ones: proprietary binaries, x86_64 only.

Four of the five stumbles along the way were bugs in my own script, not real incompatibilities, and all four would break anyone's build:

SymptomCause
Dies on the first call with pkg: unbound variable A single local expands all its values before assigning any of them
Can not use 'any' architecture with other architectures The PKGBUILD has arch=(any) unquoted, and the guard only checked for the quoted form
The AUR clone comes out empty AUR URLs use the PackageBase, which isn't always the package name: yaru-icon-theme lives in the yaru repo
failed to prepare transaction on install The PKGBUILD produces several subpackages and only one has a missing dependency. You have to build without installing, then install the specific subpackage

And a final irony: installing the Yaru icons, pacman complained about two conflicting files… created by Omarchy's own theme-system.sh, precisely because the theme wasn't installed. It's resolved with --overwrite '/usr/share/icons/*' and reapplying the links afterward.

A bash trap

The function above started like this:

local src="$1" pkg="$2" dir="/tmp/omabuild/$pkg"

Bash expands all the values in a local before assigning any of them, so $pkg doesn't exist yet when $dir is built, and with set -u the script aborts on the very first call. You have to split it into two statements.

Updates

What if I click “Update System”?

It's the question that matters most long-term, and the initial answer was “no.” Three things blocked it, and none is obvious until you read the code.

Finding 08 · Updating

The Omarchy tree never updated

omarchy-update calls omarchy-update-dev, whose first line is:

[[ $OMARCHY_PATH != "/usr/share/omarchy" ]] || exit 0

It exits immediately if OMARCHY_PATH is the canonical path, because it assumes the pacman package owns that location. On an ARM install, that's a git checkout, and nobody updates it. The system would keep receiving new packages while Omarchy's scripts, themes, and configuration stayed frozen forever. Two commands show it: 

git -C /usr/share/omarchy log -1 --format=%h    ed7bae4  (August 20)
git -C /usr/share/omarchy fetch --dry-run       ed7bae4..2c247e3  quattro

The fix fits Omarchy's own design: a hook in ~/.config/omarchy/hooks/post-update.d/ that does the git pull and links the new binaries, while respecting the ARM-specific wrappers.

Finding 09 · Safety

No safety net

omarchy-snapshot create returns 127 if snapper isn't installed, and omarchy-update treats that as “continue without a snapshot.” In other words: every update on a rolling release, with no way back. 

sudo pacman -S snapper
sudo bash -euo pipefail /usr/share/omarchy/install/config/snapper.sh

With systemd-boot there's no snapshot picker in the boot menu —that comes from limine-snapper-sync— but the snapshots exist and can be recovered with snapper rollback.

Finding 10 · Symlinks

An infinite loop hidden in a symlink

I introduced this one myself, and it's the most instructive. The wrapper was created like this:

sudo tee /usr/local/bin/omarchy-pkg-add <<'WRAP'
REAL=/usr/share/omarchy/bin/omarchy-pkg-add
...
exec "$REAL" "${avail[@]}"
WRAP

Looks correct. The problem is that /usr/local/bin/omarchy-pkg-add was a symlink into the tree, and tee follows symlinks: it replaced Omarchy's original script with the wrapper, whose REAL now pointed at itself. Every call looped until it hung the entire update.

It didn't surface earlier because it only triggers when a migration installs a package, and they were all stamped. It appeared the moment the first new migration arrived. A git status on the tree gave it away: 

 M bin/omarchy-pkg-add        ← content modified, shouldn't be
 mode change 100644 => 100755 bin/omarchy-remove-service-dropbox

Two lessons: tee follows symlinks and install doesn't, and a git checkout is a good detector for accidental writes to places that should be immutable. The second line gives away a third problem: a chmod +x left the checkout dirty, and git pull --ff-only refuses to update like that. It's fixed with git config core.fileMode false before the chmod.

Result

With that, one full cycle goes through prune, snapshot, git pull of the tree, keyring, pacman -Syu, migrations, hook, AUR, and mise:

Packaging

The UTM bundle, written by hand

UTM won't let you create machines from the command line: utmctl only manages the lifecycle. But the .utm format is documented in the source code, and a hand-written config.plist works perfectly. Three things worth knowing:

The ten top-level keys are mandatory. They're decoded with decode(), not decodeIfPresent(): omitting even an empty <array/> makes UTM reject the bundle.

The VARS half of the aarch64 UEFI firmware is edk2-arm-vars.fd, not edk2-aarch64-vars.fd, which doesn't exist. The CODE half is supplied by UTM at runtime.

UTM doesn't watch the machines folder. listRefresh() runs exactly once, at app launch. A bundle copied there while UTM is open stays invisible until you quit and reopen it.

The keys that matter for performance:

<key>Architecture</key> <string>aarch64</string>
<key>Target</key>       <string>virt</string>
<key>Hypervisor</key>   <true/>                      <!-- HVF, no emulation -->
<key>Hardware</key>     <string>virtio-gpu-gl-pci</string>
<key>UEFIBoot</key>     <true/>

Preparing the image for someone else

An image someone else is going to use carries more inside than it looks like: SSH keys, the machine-id, the SSH server's host keys, git identity, shell history, saved wifi networks, and logs. 

# machine identity (regenerates on its own at boot)
: > /etc/machine-id
rm -f /etc/ssh/ssh_host_*

# personal identity
rm -rf /home/$U/.ssh /home/$U/.gnupg /home/$U/.gitconfig /home/$U/.bash_history
rm -f  /etc/NetworkManager/system-connections/*

# logs and caches
rm -rf /var/log/journal/* /var/cache/pacman/pkg/*

# the backups usermod leaves behind contain the old user and hash
rm -f /etc/passwd- /etc/shadow- /etc/group-

# free unused space so the qcow2 compresses better
fstrim -av

Gotcha

If /usr/share/omarchy is a symlink into a user's $HOME, renaming that user breaks the system. Convert it into a real directory before renaming anything. 

# -c compresses clusters inside the qcow2: the image takes up half
# the space even once decompressed, in exchange for decompressing on read
qemu-img convert -c -O qcow2 dist.qcow2 slim.qcow2   11.6 GB → 6.6 GB
qemu-img check slim.qcow2
zip -r -1 omarchy-arm-utm.zip "Omarchy ARM.utm"

And a precaution you only learn by breaking it: after sanitizing, the image must never boot again. The first boot regenerates /etc/machine-id, the randomness seed, and the logs, and that would end up identical across every distributed copy. Verifying without dirtying it uses an overlay layer: 

qemu-img create -f qcow2 -b slim.qcow2 -F qcow2 prueba.qcow2

Result

What you get, and what you don't

Works

Native Arch Linux ARM aarch64 with HVF, linux-aarch64 kernel 7.2, btrfs with subvolumes and zstd compression, Hyprland 0.56.1 with the full Omarchy 4 stack —quickshell as bar, menu, OSD, and notifications, hyprlock, hypridle, uwsm, SDDM with autologin—, the themes, the 439 omarchy-* commands, and omarchy-update.

Doesn't work

GL acceleration inside the VM: rendering runs in software, and blur and shadows come disabled. And herdr is missing, which requires Zig 0.15 semantics while the repos are already on 0.16, on ARM and x86_64 alike. Proprietary apps don't ship inside for licensing reasons, but all of them have an official ARM64 build, and omarchy-arm-extras fetches them from their source.

And it's worth stating plainly: this is not Omarchy. It's a reconstruction of its desktop on a different base. Omarchy supports x86_64; once they ship the aarch64 ISO already on their roadmap, this work stops being necessary.

Auditing the script: 37 defects where I thought there were none

The question was simple: “do we have a single script that can install everything from scratch while dodging every known problem?” My impression was yes. I could have just answered that.

Instead of trusting the impression, I cross-checked the script against its own sources of truth —the 16 scripts in fixes/, this article's findings, a dry-run simulation on a clean Mac— and ran every finding through an independent refuter whose job was to knock it down. 37 survived, nine of them blocking. All of them had existed for days. None had ever surfaced.

They cluster into three shapes, and all three share something: the system kept working.

1 · Dead code from permissions. stage3 runs as a normal user, and it checked whether to install the optional-apps installer like this:

if [ -f /root/prov/omarchy-arm-extras ]; then

/root is 0750. An unprivileged user can't even stat inside it, so the condition comes back false without erroring. The block had gone days without ever running, silently.

2 · Destructive ordering within the same script. The sanitizer, at step 7:

rm -rf /root/prov /root/.bash_history /root/.cache

And in steps 8a and 8b, twenty-five lines below, it reads the update hook and the installer from /root/prov. It deleted its own input before using it. The log said, mildly, “wasn't in the rescue ISO,” and I had blamed the filename inside the ISO.

3 · Phases structurally incapable of failing. The systemic one, and the most interesting. The script uses set -uo pipefail without -e, and each phase returns the exit status of its last command, which is almost always an ok "...". Four of the eight phases couldn't fail:

PhaseHow it swallowed the error
buildsu - user -c stage3.sh || warn — a stage3 that blew up entirely still reported a good disk
utmmake-utm.sh … | tail -4 followed by ok — the pipe discards the exit code
verifycaptured pgrep -c Hyprland and never compared it to anything
fetchannounced “MD5 verified” even when the checksum's curl had failed

The common shape is recognizable: a success message that doesn't depend on anything. It's worth hunting for on purpose in any long script.

And one I committed in the fix itself. Adding interactive mode, I wrote a confirm using ${ans,,} to lowercase the answer. bash -n passed it clean. Testing it under a simulated terminal with expect:

build-omarchy-arm.sh: line 91: ${ans,,}: bad substitution

${var,,} is a bash 4 feature, and macOS ships bash 3.2, where an expansion error aborts the whole function: confirm didn't return “no,” it returned garbage, and the script carried on as if you'd said yes. A bug from the same family as the ones I was fixing, committed while fixing them. bash -n validates syntax, not semantics or version.

And the only test that counts: running it. With all 37 fixes in place, everything checked by reading, and the payloads byte-for-byte in sync, the same question remained. A full build from scratch, eight phases, on an M3 Max. It found three more bugs that no read-through had caught:

BugHow it showed up
VM_FULLNAME=Omarchy ARM unquoted in config.envon source, ARM got executed as a command → chroot died with rc=127
verify's heredoc left unquotedthe host's bash expanded the $(…), so the checks ran on the Mac: systemctl: command not found
spice-vdagentd is a static unitsystemctl enable on it does nothing; you have to enable the .socket instead

The first two I introduced while fixing the other thirty-seven. The third had been there from the start. And the result, with everything now fixed: 

16/17 tools built (only herdr fails, because of the Zig version)
extras=yes  menu=yes  hook=yes   ← the three blockers, resolved
verify inside guest: H=1 Q=1 BINS=439 BROKEN=1 UNITS=7 VER=4 CLIP=5/5 → VERDICT_OK
final image: 3.6 GB · 76 min (from deps to package, everything included)

That extras=yes menu=yes hook=yes is the proof that matters: they're the same three that had gone days without ever installing, silently, and that no previous run had flagged because the script declared itself successful regardless.

Reproducing it

The full process lives in a single script with resumable phases. If what you want is to run it, the build guide covers the requirements, what it asks, how long each phase takes, and what to do if it fails. Here's the essential part: 

./build-omarchy-arm.sh              # asks the minimum and builds
./build-omarchy-arm.sh --yes        # unattended, default values
./build-omarchy-arm.sh --from build # resume from a phase
./build-omarchy-arm.sh --list       # list the phases

Phases: deps, fetch, prepare, build, utm, verify, sanitize, package.

With a terminal it asks six things, all pre-filled from what it detects on the Mac —timezone from /etc/localtime, keyboard from macOS preferences, cores and RAM from sysctl—, so you can answer them all with Enter. Three change the outcome: whether to build the tools (~40 min), whether to include OBS Studio and Pinta (~45 min, the most expensive part of all), and whether to prepare the image for distribution. Choosing “VM for yourself” trims the phases to deps…verify and keeps your user. Without a terminal, or with --yes, it asks nothing and builds the complete image, ready to distribute.

The prepare phase deserves a comment. Instead of carrying a fixed package list, it computes one on every run by cross-referencing Omarchy's live branch against the Arch Linux ARM index. That way the build doesn't break when Omarchy changes its packages —which it will—, and it reports what got left out along the way.

Closing

What the exercise teaches

Almost all the time went into things you can't anticipate by reading documentation: a default branch that isn't the one the project documents, a distribution-model change mid-version, a compositing bug that only isolates by comparing two different terminals, and a state machine —migrations— that an installer initializes and a git clone doesn't.

The pattern that paid off the most was building the discriminating test: when windows weren't rendering, comparing foot against alacritty pointed to the cause in a minute, after a good while flailing at environment variables. And the mistake that cost the most time was trusting a test method —launching applications over SSH— that didn't reproduce the real conditions.
